## 3. Mechanism: the iter-2-peak-then-regress is an intrinsic, schema-independent W6-recipe property

Both schemas (96-d and 110-d v3) rise to an iter-2 gate peak and then
regress. The shape is **reproduced across both representations**, so it
is a property of the W6 `mcts-distill` loop recipe, not of the feature
schema. Significance: the 96-d production claim of 0.6479 is itself
**W6's transient iter-2 peak**, not a stable optimum — the same recipe
ceiling caps the production model and the v3 reproduction alike.

Verified causes (file:line ground truth from a code-grounded
investigation; treat as established):

- **Self-play data is per-iter only, no replay buffer**
  (`training/r12_orchestrator.py:154,184`). Each distill consumes only
  that iteration's self-play rows.
- **Distill warm-starts from the moving promoted checkpoint each iter,
  and the KL anchor also targets the moving promoted checkpoint (NOT a
  fixed SL init)** (`training/r12_orchestrator.py:320`). The anchor only
  damps single-step change; it provides **zero cumulative anti-drift**.
  (Correction: an earlier session statement that the anchor was fixed to
  R7b2/iter-000 was WRONG; the anchor moves with the promoted ckpt.)
- **Distill targets get monotonically softer each iter** (visit-entropy
  rises); val accuracy decays monotonically from iter-0
  (110-d: 0.740 → 0.735 → 0.711 → 0.652; same shape at 96-d). The gate
  peak at iter-2 is the net of search + rule-bot rollout masking a
  not-yet-too-rotten prior, crossing rising prior rot.
- **In rollout-leaf mode the trained value head is never used at
  gate/self-play** (`backend/src/sim/mcts.ts:552-555`). All
  crossover/pearson diagnostics are therefore causally inert symptoms,
  not gate drivers.

Ranked causes:

1. **Policy-prior degradation via per-iter distill on softening
   self-targets** — strongest; direct gate driver.
2. **Catastrophic forgetting through the warm-start chain with an
   ineffective moving KL anchor** — the mechanism behind (1).
3. Value-head degradation — **REFUTED for rollout-leaf** (value head
   unused at gate/self-play).
4. Prior over-sharpening — **REFUTED** (targets soften, not sharpen).
5. Ratchet/floor effect — explains non-recovery after the peak, not the
   peak itself.

**Root cause of low CPU utilization: the run used 4 workers on a
32-core box (`nproc`=32) → ~28 cores idle.** GPU is correctly idle
(497KB model, 0.08ms inference; CUDA EP broken anyway — out of scope).

**Trajectory-neutrality verdict (verified):** raising the worker count
is bit-comparable to the 4-worker baseline. Both stages build a fixed
seed-indexed task set independent of worker count
(`mctsSelfPlay.ts:120` seed=`seedStart+index`; `evalGate.ts:46`

across processes (`partitionSeeds`/`partitionTasks`,
`mctsSelfPlay.ts:158`, `evalGate.ts:126`). Per-game RNG is seeded
solely from the game seed (`mctsSelfPlay.ts:255`
`createSeededRng(seed:selfplay)`; `evaluateModelVsHeuristic.ts:269`
`createSeededRng(seed:modelSide)`) with no worker/PID/order input.
Worker count is therefore a pure distribution knob.

**Fix (Deliverable 1, landed):** `r12_orchestrator.py` `--workers`
default 1 → 24 (commit below). Overridable; targets a 32-core box with
headroom for the single `serve_onnx` process + OS.

`serve_onnx` (`ThreadingHTTPServer`, one shared thread-safe ORT
`InferenceSession`) is not expected to bottleneck at 24 workers given
~7% predict share at batch=1; a cheap `ort_threads` knob exists

decision time, and would be unusable in any v3.x featurizer.

- **player side wl_lower ∈ [0.5500, 0.5540]** (σ=0.0018)

- **Δ player vs opp ≈ 0.067-0.074** in every run

half of it (player 0.55 → 0.59) would lift overall wl_lower to ~0.605
— **decisively clearing the LIFT band (≥0.6040)** that no recipe lever
has crossed.
